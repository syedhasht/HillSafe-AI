HillSafe AI - Complete Project Documentation
============================================

1. Project Overview
-------------------

HillSafe AI is a mobile and web-backed early warning system for landslide and weather-related hazard monitoring. The system is designed around two user groups:

1. Community users who need location-based risk awareness, safety messages, SOS support, incident reporting, and safe check-ins.
2. Authority users who need monitored-region visibility, alerts, reports, SOS tracking, and user safety status.

The main idea is simple:

The mobile app collects the user's current GPS location. The backend decides whether the user is inside or near a monitored hazard zone. If the user is outside monitored danger areas, the system returns NO RISK. If the user is inside or near a monitored zone, the backend enriches the location using weather and terrain APIs, runs the machine learning risk pipeline, stores useful data in the database, and returns a risk score, risk level, and safety message.

The system is deployed with:

- Flutter Android app for users and authority users
- Django REST API backend
- Neon PostgreSQL database
- Render web service deployment
- Firebase Cloud Messaging for push notifications
- Gemini API for the safety assistant

Production backend:

https://hillsafe-ai.onrender.com

Production API base:

https://hillsafe-ai.onrender.com/api

9. Monitored Region Model
-------------------------

The Region model represents known monitored hazard areas such as Murree, Swat, Kohistan, Hunza, Skardu, and related northern Pakistan regions.

Important fields include:

- name
- district
- latitude
- longitude
- current_risk_score
- current_temperature
- current_rainfall
- current_humidity
- last_updated
- is_critical_zone
- danger_radius_km
- warning_radius_km

The hazard radii are important because the app should not blindly classify every flat area as risky. If a user is far from monitored hazard zones, the backend can return NO RISK directly.


10. TerrainSample Model
-----------------------

TerrainSample stores terrain and soil data for a coordinate. The backend rounds latitude and longitude to a stable key and stores fetched data.

Stored values include:

- latitude_key
- longitude_key
- requested_latitude
- requested_longitude
- elevation_m
- slope_degrees
- elevation_code
- slope_code
- soil_type
- soil_code
- clay_percent
- sand_percent
- silt_percent
- lithology_type
- lithology_code
- ndvi_code
- ndwi_code
- data_quality
- fetch_errors

Why this exists:

Free public APIs have rate limits. Storing the result in the database reduces repeated calls and makes future predictions faster for nearby coordinates.


11. Main Prediction Pipeline
----------------------------

Primary endpoint:

POST /api/predict/location-risk/

Input:

{
  "latitude": 34.909,
  "longitude": 73.649
}

High-level flow:

1. Flutter gets the user's GPS coordinates.
2. Flutter sends latitude and longitude to the backend.
3. Backend finds the nearest monitored region.
4. Backend checks if the user is:
   - inside_hazard_zone
   - near_hazard_zone
   - outside_monitored_hazard_zone
5. If outside monitored zone, backend returns NO RISK.
6. If inside or near monitored zone, backend fetches live weather.
7. Backend checks TerrainSample table for existing terrain data.
8. If terrain data is missing, backend fetches OpenTopoData and SoilGrids.
9. Backend converts raw data into model feature codes.
10. Random Forest model predicts risk score.
11. Backend returns risk score, risk level, safety message, nearest region, weather, terrain, and input features.

The prediction logic belongs in the backend, not in Flutter. Flutter should display results and collect device/user input only.


12. Hazard Zone Gating
----------------------

Hazard zone gating prevents wrong risk warnings in flat or unrelated areas.

Zone meanings:

inside_hazard_zone
  The user is inside the direct danger radius of a monitored region.

near_hazard_zone
  The user is inside the warning radius but outside the direct danger radius.

outside_monitored_hazard_zone
  The user is far from monitored hazard regions. The system should return NO RISK directly.

This design matches the real use case:

If a region is critical and the user is near that region, the user gets an alert or risk message. If the user is in a plain/safe area far away, the app should not show moderate risk only because generic model features happened to produce it.


13. Risk Levels
---------------

Risk score is a decimal probability.

Examples:

- 0.10 means 10%
- 0.30 means 30%
- 0.85 means 85%

Displayed risk levels:

NO RISK:
  Below 15%, or outside monitored hazard zones.

LOW:
  Around 15% to below 30%.

MODERATE:
  Around 30% to below 70%.

HIGH:
  Around 70% and above.

The frontend should display percentages by multiplying risk_score by 100.


14. Safety Messages
-------------------

The backend returns one main safety message per prediction. This avoids flooding the user with many different messages.

Messages are based on:

- zone status
- risk level
- ML score

Examples:

outside_monitored_hazard_zone:
  No monitored hazard region is close to your current position. Continue normal activity, but stay aware of weather updates if you are travelling.

near_hazard_zone:
  You are near a monitored hazard zone, but not inside the immediate danger area. Stay updated and avoid unnecessary travel toward the risky region.

inside_hazard_zone:
  You are currently inside a high-alert hazard zone. Stay cautious, avoid risky movement, and follow official safety guidance immediately.

HIGH:
  A high hazard risk has been detected near your location. Move away from dangerous slopes, riverbanks, and unstable roads as soon as it is safe to do so.

16. Elevation and Slope Data
----------------------------

Provider:

- OpenTopoData

Dataset:

- srtm30m

Endpoint:

https://api.opentopodata.org/v1/srtm30m

Method:

The backend requests elevation for five nearby points:

- center
- north
- south
- east
- west

From these values it calculates approximate slope. It then stores elevation and slope in TerrainSample.

Why this matters:

Slope and elevation are important landslide factors. A flat area should generally have lower hazard contribution than a steep mountainous area.


17. Soil Data
-------------

Provider:

- SoilGrids

Endpoint:

https://rest.isric.org/soilgrids/v2.0/properties/query

Fetched properties:

- clay
- sand
- silt

Depths:

- 0-5cm
- 5-15cm

The backend classifies soil into a simple soil type/code and stores it in TerrainSample.

19. ML Feature Handling
-----------------------

The Random Forest model expects coded feature inputs. Current important derived inputs include:

- precipitation from OpenWeather
- elevation from OpenTopoData
- slope from OpenTopoData-derived slope
- lithology currently defaulted
- NDVI currently defaulted
- NDWI currently defaulted

Known limitation:

The current model still needs stronger real GIS enrichment for lithology, NDVI, and NDWI. The project has improved beyond dummy values by adding weather, elevation, slope, and soil storage, but full scientific accuracy needs better official GIS raster/vector datasets and model retraining.


20. Region Risk Refresh
-----------------------

Endpoint:

GET /api/regions/

This endpoint returns monitored regions. It also refreshes stale region risk values through the ML pipeline. This prevents old hardcoded 10% values from staying forever.

Manual refresh endpoint:

POST /api/ingest/trigger/

This endpoint recalculates region risk and can generate alerts when needed. It is useful for cron jobs or manual maintenance, but the app should not require the user to run it manually every time.

How region refresh works:

1. Backend checks Region.last_updated.
2. If region data is stale, it calls the shared risk pipeline.
3. It fetches weather and terrain.
4. It predicts risk.
5. It updates current_risk_score and weather fields.
6. Flutter receives fresh region data.


21. Alerts and Push Notifications
---------------------------------

Authority users can create alerts from the dashboard.

Alert creation endpoint:

POST /api/alerts/create/

Alerts are saved in the database and can be shown in the app's alert feed.

Push notifications use Firebase Cloud Messaging.

Important behavior:

Only users whose latest stored device coordinates are within 20 km of the selected alert region should receive the push notification.

Device location registration endpoint:

POST /api/accounts/save-device-token/

The Flutter app sends:

- Firebase token
- device type
- latitude
- longitude

The backend stores the token and latest coordinates in accounts_devicetoken. When an authority creates an alert for a region, the backend calculates distance between the selected region and device coordinates. Only devices inside the radius are targeted.

Important limitation:

If a user never opened the app, denied notification permission, or denied location permission, that device may not have a usable token/location pair for targeted push delivery.

25. AI Safety Assistant
-----------------------

Endpoint:

POST /api/chatbot/

Provider:

- Gemini API

The chatbot should not pretend to perform live landslide prediction inside chat. For live risk questions, it should guide the user to the dashboard or weather/risk card.

Correct chatbot behavior:

- Give safety guidance
- Explain what to do during landslide/flood/weather risk
- Encourage using dashboard for live risk status
- Avoid claiming it can independently predict live risk
- Avoid overconfident emergency claims

API key:

- GEMINI_API_KEY in backend environment variables

The Gemini key must stay in Render environment variables and should not be committed.

33. Known Limitations
---------------------

The system is functional, but these limitations should be understood during evaluation:

1. Lithology, NDVI, and NDWI are still defaulted until real GIS layers are integrated.
2. Soil data is stored, but the current Random Forest feature array may not directly use soil depending on the trained model schema.
3. Terrain slope is approximated from OpenTopoData point elevations, not from a local high-resolution GIS raster.
4. Render free hosting can sleep and cause slow first requests.
5. Public APIs have rate limits.
6. The LSTM model exists but is not the primary live risk path.
7. Region analytics are partly derived from current region risk and may need historical tables for advanced trend analysis.
8. The trained model quality depends on the original training dataset and feature engineering.


34. Recommended Future Improvements
-----------------------------------

For better scientific accuracy:

- Add official GIS raster layers for slope, aspect, curvature, NDVI, NDWI, lithology, land cover, and drainage.
- Store raster-derived values in TerrainSample.
- Retrain the model using the exact same feature set used in production.
- Add a historical prediction table for trend analytics.
- Add admin tools for editing hazard radius per region.
- Add stronger authority verification.
- Add offline emergency guidance inside Flutter.
- Add better map overlays for danger and warning radii.
- Add audit logs for alert creation and SOS handling.

36. Summary
-----------

HillSafe AI is a complete disaster-risk awareness system with a Flutter app, Django backend, ML prediction pipeline, Neon database, Render deployment, Firebase push notifications, and Gemini safety assistant.

The most important design decision is that prediction happens in the backend. The frontend collects location and displays results. The backend decides if the user is inside a monitored hazard zone, fetches live weather and terrain data, runs the model, stores useful samples, and returns a clear risk level with one safety message.

This makes the system easier to maintain, easier to deploy, and more suitable for real-world evaluation.
